Questionable Candy

A candy shop website with a dash of satire. Every candy has to admit what is wrong with it, checkout warns you about the sugar, and you confirm your order three times before it is placed.

What it does today

A customer can go from the catalog to a placed order: browse, read about a candy and its flaw, fill a cart, sign up or log in, read a health warning based on the cart, confirm, and get a receipt. No payment is taken, so every order stays "pending".

Decisions we made

The main technical choices, why we made them, and what each rules out. The theme is consistent: use what Django already provides, and add a tool only once it has been shown to be needed.

Pages built by the server

Partly replaced
Decision 1

Django renders each page as plain HTML, styled with our own CSS. No front-end framework such as React.

Why
Try Django's own tools first.
Rules out
React, Vue, Tailwind, a build step.

The "no interactivity library" half was replaced by decision 6. Full record

Django's own login system

Accepted
Decision 2

Logins use Django's built-in sessions, with its standard protection against forged requests.

Why
It works with no extra software, and Google login can be added on top later without redoing it.
Rules out
Login tokens, one-time codes, for now.

Full record

One Django application

Accepted
Decision 3

A single Django site with no separate API. The business rules live with the data they govern.

Why
Nothing needs an API yet. One can be added if a mobile app ever does.
Rules out
Django REST Framework, FastAPI, Flask. An automatic check blocks the first.

Full record

PostgreSQL everywhere

Accepted
Decision 4

The same database in development, testing and production.

Why
Allergy lists use a PostgreSQL feature, and testing on a different database would not test what runs.
Rules out
SQLite, MySQL, MongoDB.

Where candy pictures will be stored is still undecided. Full record

A small, standard testing toolkit

Accepted
Decision 5

pytest for the tests, factory_boy for test data, and Playwright to drive a real browser. At least 95% of the code must be tested.

Why
The professional standard for Django, and kept simple: a few well-known tools rather than many.
Rules out
Nothing fixed. More tools can be added when a real need appears.

Full record

Small scripts for interactivity

Accepted
Decision 6

Two small libraries, htmx and Alpine.js, update parts of a page (such as the cart button) without reloading it.

Why
The first interactive feature showed plain page reloads were clumsy.
Rules out
A front-end framework or build step. The scripts load from a public server, locked to an exact file.

Full record

Our own user record

Accepted
Decision 7

The site has its own user type, so each customer's allergies are stored on their account.

Why
This is cheapest to set up before any users exist. Adding more to user later is easier this way.
Rules out
Changing the user type again without careful migration work.

Full record

Hand-written styles, light and dark

Accepted
Decision 8

One stylesheet, with a light and a dark theme that follow your system setting or a toggle.

Why
No extra software and no build step, and the site is small enough for one file.
Rules out
Tailwind and other style frameworks, web fonts. For now.

Still open

Questions that need an answer from you. None of them blocks the current site.

  • Which payment provider?Nothing is charged until one is chosen. Also open: what to do if only part of an order can be fulfilled.
  • Where do candy pictures live?They are fixed files today. Uploading needs a storage decision.
  • Guest checkout?Ordering currently needs an account.
  • Google or other logins at launch?Only username and password exist today.
  • Flaw format?Free text today, or a category plus a description?
  • A long catalog?Pages, or endless scrolling, once there are many candies.
  • Record what the site already settled.Login timing, the warning's content and the confirmation layout were decided while building, but the requirements document still lists them as open.
Why some of these are harder than they look

Guest checkout, when to require a login, and which logins to offer are one question in three parts. Answer them together. Choosing a payment provider also decides what "paid" means for an order, which today can only ever be "pending".
